What is HTML-First?

Last updated November 2026 · Reviewed against the IndexHot GEO Measurement Standard v1.0

HTML-first is an architectural choice: the content a page exists to deliver is present in the initial HTML response, before JavaScript runs. Everything else, styling, interaction and personalisation, is layered on afterwards.

In short: Content present in the first HTML response, before any script runs.

Why the choice is structural, not stylistic

A page that requires rendering is readable by clients that render and invisible to clients that do not. Since pipelines differ in budget rather than in principle, a render-dependent page is readable sometimes. HTML-first removes the dependency, which converts a probabilistic outcome into a deterministic one.

What HTML-first does not forbid

  • Client-side interaction: filtering, calculators, modals, all still fine.
  • Personalisation after load: a default state in HTML, personalised afterwards.
  • Frameworks: server rendering or prerendering does the same job with the same tooling.
  • Modern design: the constraint is on where content lives, not how it looks.

Testing it

Disable JavaScript, reload, and read the page. Whatever is missing is the gap between your intent and what some pipelines receive. Repeat on the ten pages whose claims you need cited, and treat a missing paragraph as an engineering ticket rather than a copy problem.

Frequently asked questions

Is HTML-first the same as static?

Static is one way to achieve it. Server rendering and prerendering achieve it with dynamic back ends.

Does it hurt performance?

Usually it improves first paint, since content no longer waits for a script.

What about sites that must render?

Render the content routes and keep the interactive parts client-side. The rule is about content, not the whole page.
