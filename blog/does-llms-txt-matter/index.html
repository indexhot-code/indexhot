Does llms.txt actually matter? What the evidence shows

By IndexHot Team · November 26, 2026 · 7 min read

llms.txt is a plain-text file at the site root that proposes telling AI systems which pages matter. It is widely recommended and thinly evidenced. This is what it actually does, what we have been able to observe, and the one job it performs well regardless of whether any model reads it.

What the proposal claims

The file proposes a curated index: a list of the pages a site considers most useful to an AI system, with short descriptions, in a format that is cheap to parse.

The reasoning is plausible. A retrieval pipeline that could read such a file would skip navigation, boilerplate and abandoned pages. The problem is that plausibility is not adoption, and no major answer engine has published a commitment to reading it.

  • It is a community proposal, not a specification maintained by a standards body.
  • No platform has documented consuming it as a retrieval input.
  • Absence of adoption does not prove it is ignored; it means the effect is unmeasurable from outside.

What we can and cannot observe

We can observe whether a file is requested: server logs show fetches by user agents, and a crawler that reads the file leaves a trace. Across the sites we have access to, requests for llms.txt are rare and predominantly from tooling rather than from answer engines.

We cannot observe internal use. A system could consume the file without a distinguishable request pattern, or could read it and ignore it. So the honest statement is narrower than either camp: there is no evidence of benefit, and no proof of harm.

That places llms.txt in the same category as several other speculative signals. Publishing it costs ten minutes and a text file. The mistake is spending a quarter on it, or treating it as a substitute for making pages fetchable.

Where it is genuinely useful

The file forces a decision most sites never make: which twenty pages would you want a machine to read first. Answering that question produces an editorial inventory, and the inventory is valuable whether or not the file is ever consumed.

It also surfaces duplication. Sites that cannot produce a coherent short list usually have forty pages that all claim to be the definitive overview, which is a real problem independent of llms.txt.

  • Use it as a maintenance checklist: the listed pages should be the ones with the most extractable substance.
  • Keep the descriptions factual, because they are also readable by humans who open the file.
  • Update it when pages move, or the inventory decays into a list of redirects.

What to do instead, in priority order

  1. Make sure the pages return real HTML with the substance in it. This is the condition that decides everything else.
  2. Fix status codes and canonical tags so the crawlable set equals the indexable set.
  3. Put the key facts in the first sentence of each section, where a chunk can carry them.
  4. Publish schema that states the entity, the author and the page type.
  5. Then, if you have ten minutes left, write llms.txt as an inventory.

That order is not a dismissal. It is the order in which the failures actually occur, and llms.txt sits near the end because its effect is unmeasurable while the earlier items are testable in an afternoon.

Frequently asked questions

Will publishing llms.txt hurt anything?

Not measurably. It is a static text file. The cost is the opportunity cost of the time, which is trivial for one page and significant for a programme.

Should I wait for a standard?

No. Make the file if it helps the inventory, but do not gate other work on adoption that has not happened.

Is it the same as robots.txt?

No. robots.txt governs access and is honoured by crawlers. llms.txt proposes curation and has no enforcement behind it.
