Mention, describe, recommend: three different wins

By IndexHot Team · November 26, 2026 · 8 min read

Being named in an answer, having the answer make a claim about you, and being recommended for a specific situation are three distinct outcomes. Most reporting collapses them into one, which is why teams celebrate mentions that produced no enquiries and miss recommendations buried inside paragraphs.

The three states

State What the answer does What it implies
Named Lists the brand among options The model knows it exists
Described Makes a claim about it: price, capability, limit The model has evidence it can state
Recommended Names it for a defined situation or use case The model holds a positioning, not just a fact

The progression is real but not automatic. A described brand is not necessarily recommended, and a recommended brand is usually described as well, which is why coding the highest state reached is the only sensible rule.

Why mentions overstate success

A list of six names includes four that are merely present. If your rate improved because you entered three lists as a tail item, nothing commercially changed, and the report will be believed until somebody asks why enquiries did not move.

The test is quick: does the answer say anything about you that a buyer could act on? If not, you are named and nothing more, which belongs in a different column.

  • Named only: appears in a list, no claim attached.
  • Described: at least one checkable attribute appears.
  • Recommended: the answer suggests the brand for a stated condition or buyer.

What each state requires

Named requires presence: an entity the model can connect to the category, and enough corroboration to include it in an option set.

Described requires extractable facts: a price, a limit, a capability, stated in a form a chunk can carry. Generic positioning produces naming without description.

Recommended requires positioning: a specific situation the brand is matched to, which usually has to be stated on the site in those terms rather than implied. An answer cannot recommend you for a use case your pages never claim.

That last point is where most programmes stall. They add facts, which moves described, and never state who the product is for, which is the missing input for recommended.

How to code it without over-engineering

  1. Read the answer and ask one question: is there a claim about this brand, or only a name?
  2. If there is a claim, ask whether the answer assigns the brand to a situation or buyer.
  3. Record the highest state reached, plus the sentence that justified it, so the coding can be reviewed.
  4. Calibrate with a second coder on twenty answers before trusting a rate.

Two coders, twenty answers, one month of work. That is enough to make the column defensible, and far cheaper than reconstructing it later from memory.

Frequently asked questions

Is recommendation the same as absorption level three?

Effectively yes. Recommendation-level absorption is the coding rule for this state.

Do all surfaces recommend?

Some do it more explicitly, through ranked lists or a direct suggestion. Others only describe, and the recommendation is implied. Code what is written, not what you infer.

How do I increase recommendations?

State the use case on the page: who the product is for, at what scale, in what situation. Then make the supporting facts extractable so the claim can be carried.
